# KRISHI AI Project Audit

Audit scope: the current repository source, `frontend/app.py`, backend route registration, standalone RAG/demo scripts, `requirements.txt`, `.gitignore`, README/quick-start/status documentation, and literal frontend API call sites. The audit does not include the vendored `venv/` directory.

## 1. Backend Endpoints

The Flask application in `backend/main.py` mounts these blueprints:

- `/api/auth` from `backend/routes/auth_routes.py`
- `/api/user` from `backend/routes/user_routes.py`
- `/api/crop` from `backend/routes/crop_routes.py`
- `/api/farm` from `backend/routes/farm_routes.py`
- `/api/fertilizer` from `backend/routes/fertilizer_routes.py`
- `/api/history` from `backend/routes/history_routes.py`
- `/api/soil` from `backend/routes/soil_routes.py`
- `/api/weather` from `backend/routes/weather_routes.py`

Frontend usage below is based on literal URL searches in `frontend/`. A route is marked "called" only when a frontend request targets that path or path family.

### Authentication routes

| Method and path | What it does | Input | Return | Frontend status |
|---|---|---|---|---|
| `POST /api/auth/signup` | Creates a user through `auth_controller.signup`, `auth_service.signup_user`, bcrypt, and MongoDB. | JSON object with `username` and `password`. | JSON success/message response, or validation/database/user-exists failure. | **Called** by `frontend/app.py:416`. |
| `POST /api/auth/login` | Checks credentials and returns a JWT generated by `auth.jwt_handler.generate_token`. | JSON object with `username` and `password`. | On success: `success`, `message`, and `token`; otherwise an error message. | **Called** by `frontend/app.py:435`. |

### Duplicate user routes

| Method and path | What it does | Input | Return | Frontend status |
|---|---|---|---|---|
| `POST /api/user/signup` | Uses the separate `controllers/user_controller.signup` path. | JSON object with `username` and `password`; route indexes both keys directly. | JSON result from the user controller. | **Orphaned**. The frontend uses `/api/auth/signup`, not `/api/user/signup`. |
| `POST /api/user/login` | Uses the separate `controllers/user_controller.login` path. | JSON object with `username` and `password`. | JSON result from the user controller, using a different JWT implementation. | **Orphaned**. The frontend uses `/api/auth/login`. |

The two authentication families are not equivalent: `/api/auth/*` uses `auth_service` plus `auth.jwt_handler`, while `/api/user/*` uses `controllers/user_controller` and a different secret/payload implementation.

### Crop routes

| Method and path | What it does | Input | Return | Frontend status |
|---|---|---|---|---|
| `POST /api/crop/recommend` | Protected crop recommendation route. It now calls `run_advisory_pipeline`, so it performs the existing recommendation, risk check, RAG retrieval, and Groq synthesis. | JSON farmer input. Required in practice: `location`; normal requests also provide `latitude`, `longitude`, `soil`, `N`, `P`, `K`, and `ph`. | The original recommendation fields plus `risk_flagged`, `risk_level`, `risk_flags`, `knowledge`, and `advisory_text`. | **Orphaned by the current frontend.** `frontend/app.py` now calls `/api/crop/advisory`, not this path. |
| `POST /api/crop/advisory` | Protected agentic crop recommendation endpoint. Runs the LangGraph pipeline. | Same farmer input JSON as the recommendation flow. | JSON containing `success`, `recommended_crop`, `top_3`, weather, soil info, fertilizer, mapped location, risk information, retrieved knowledge, and LLM advisory text. | **Called** by `frontend/app.py:646`. |
| `POST /api/crop/advisory/pdf` | Protected endpoint that runs the pipeline again, creates a PDF, and sends it as an attachment. | Same farmer input JSON. | `application/pdf` attachment named `krishi_advisory.pdf`; failed recommendation returns JSON with status 400. | **Called** by `frontend/app.py:763` when the recommendation result is rendered. |

All crop routes require `Authorization: Bearer <JWT>` through `token_required`.

### Farm routes

| Method and path | What it does | Input | Return | Frontend status |

No request in `frontend/`. The route is also not protected by JWT. |

### Weather route

| Method and path | What it does | Input | Return | Frontend status |
|---|---|---|---|---|

### Application root

`GET /` is defined directly in `backend/main.py`, not under `backend/routes/`. It returns `{"msg": "Backend running"}` and is not called by the frontend.

### Supporting backend modules

- `backend/auth/auth_controller.py` is the active `/api/auth` signup/login adapter and is used by `auth_routes.py`.
- `backend/auth/auth_service.py` is the active bcrypt-backed user lookup/create/login implementation and is used by `auth_controller.py`.
- `backend/auth/auth_middleware.py` protects crop, soil, and history routes and stores the decoded user ID in `flask.g`.
- `backend/auth/jwt_handler.py` generates/verifies tokens for the active auth route, but its hard-coded secret does not match the `.env` secret used by the older controller path.
- `backend/database/mongo.py` loads `.env`, opens MongoDB, and exposes `users_collection`, `history_collection`, and `soil_collection`.
- `backend/utils/validation.py` validates location, optional NPK values from 0 to 150, and optional pH values from 0 to 14.
- `backend/utils/translations.py` contains a separate English/Hindi translation dictionary, but `frontend/app.py` defines and uses its own translation dictionary instead. No backend caller uses this module.
- `backend/logging_config.py` configures JSON logging for the application and Werkzeug.

### Standalone tools

- `test_rag.py` is a root-level standalone RAG demo. It loads the nine text files under `rag_standalone/knowledge`, embeds them locally, persists `rag_standalone/vector_store/index.faiss` and `documents.json`, and exposes `retrieve(query, k=3)`. It is not imported by the Flask backend.
- `backend/test_advisory_pipeline.py` is an end-to-end smoke test. It imports the Flask app to supply an application context, runs four real farmer cases, calls the recommendation/RAG/Groq/PDF path, prints full results, and exits nonzero when advisory text or PDF creation fails.

## 3. Frontend - What a User Actually Sees

The only frontend application file is `frontend/app.py`. It is a single Streamlit script that reruns from top to bottom on interaction.

### Initial page and styling

1. Streamlit sets the page title to `KRISHI AI`, uses a wide layout, and opens with the sidebar expanded.
2. A large CSS block applies a near-black dark dashboard theme: dark app and sidebar surfaces, green/gold accents, light text, dark inputs, dark alerts, dark tables, dark metric cards, borders, and shadows.
3. The app defines English and Hindi translations locally. The visible translated labels include the title, subtitle, login/signup labels, language settings, logout, dashboard, map/voice input choices, soil/NPK/pH labels, recommendation labels, confidence, weather, fertilizer, history, loading, success, and error messages.
4. It hard-codes a frontend location dictionary with coordinates for Delhi, Meerut, Punjab, Haryana, Uttar Pradesh, Bihar, West Bengal, Jharkhand, Maharashtra, Madhya Pradesh, Karnataka, Tamil Nadu, Telangana, and Andhra Pradesh.
5. It hard-codes Hindi crop names, yield estimates, profit estimates, and a small regional best-crop dashboard table.

### Sidebar

- A `Settings` heading is always visible.
- A language selectbox offers `English` and `hindi` and updates `st.session_state.language`.
- After login, a voice-language selectbox offers English/Hindi for text-to-speech.
- After login, a Logout button clears the JWT session state and reruns the app.

### Unauthenticated screen

When no token is stored:

- The page header shows `KRISHI AI` and `Smart Crop Recommendation System`.
- A `Login / Sign Up` heading is shown.
- A username text input is shown.
- A password input is shown with password masking.
- A `Sign Up` button posts the credentials to `/api/auth/signup`; success or failure is shown as a Streamlit success/error message.
- A `Login` button posts the credentials to `/api/auth/login`; on success it stores the returned token and reruns the page. Connection, timeout, and general exceptions show error messages.

### Authenticated dashboard

After login:

1. A `Dashboard` heading appears.
2. A `Best Crops by Region` table displays the hard-coded region table for Delhi, Punjab, Haryana, Uttar Pradesh, and Bihar. It shows region, crop, confidence, and estimated profit per hectare.
3. The app calls `/api/history/` with the JWT. If records exist, a `Your Recent Recommendations` table shows up to five records with number, location, crop, confidence, and estimated profit. If there are no records it shows `No recommendations yet`; failures show `Could not load history`.

### Location selection

The user sees `Select How to Choose Location` with a radio control containing:

- `Use Map`
- `Say Location`

#### Map mode

- A heading instructs the user to click the map.
- A Folium OpenStreetMap map is displayed at a default Delhi-centered view.
- If a location was selected, a green marker is shown.
- Clicking the map finds the nearest frontend location, displays a success message with the city, stores it in session state, and reruns.

#### Voice mode

- A heading asks the user to say a location name.
- A `Listen for Location` button opens the microphone through `SpeechRecognition` and attempts Google speech recognition.
- Recognized text is displayed.
- The frontend matches the text against its own location dictionary. A match is saved and displayed as a success message.
- If no exact/partial match is found, the frontend falls back to Delhi, displays a warning, and preserves the original voice text for later speech output.
- If speech recognition returns nothing, an error message is shown.

### Crop analysis form

Below the location selector:

- A `Crop Analysis` heading appears.
- The selected location is shown as a success message, or the app warns that the user should select a location and temporarily uses Delhi.
- A soil-type selectbox offers `Loamy`, `Sandy`, `Clay`, `Silty`, and `Peaty`.
- A Nitrogen number input ranges from 0 to 500 and defaults to 90.
- A Phosphorus number input ranges from 0 to 500 and defaults to 40.
- A Potassium number input ranges from 0 to 500 and defaults to 40.
- A pH number input ranges from 4.0 to 9.0, defaults to 7.0, and steps by 0.1.
- Before the submit button, the app requests weather for the selected frontend location and uses a fallback weather object of 25 C, 50% humidity, and Clear if the request fails.

### Recommendation submission and result screen

When the user clicks `Get Recommendation`:

1. The app ensures a selected location exists, builds a request payload containing location, coordinates, soil, NPK, pH, weather values, and a hard-coded rainfall value of 100.
2. It posts the payload and JWT to `/api/crop/advisory`.
3. The backend response retains the original crop recommendation fields and adds risk, RAG, and advisory fields.
4. If the response is unsuccessful, the frontend displays the returned error message.
5. On success, the app derives the best crop, Hindi crop name, estimated profit, mapped location, and fertilizer values.
6. It speaks a location/crop/fertilizer message through gTTS in the selected voice language, saves `output.mp3`, and attempts to play it with macOS `afplay`.
7. It clears the stored voice input text.

The result display then contains:

- Three dark result cards:
  - `Recommended Crop`, showing the crop, Hindi name, and selected location/mapping note.
  - `Confidence`, showing the first top-three confidence as a percentage.
  - `Risk Level`, showing low/moderate/high and the number of flagged conditions.
- A `Risk Overview` Plotly gauge with a 0-100 display. The app maps low to 25, moderate to 60, and high to 90. Gauge colors are green, gold, and red-toned respectively.
- A risk warning alert listing each backend risk flag when flags exist.
- An `Advisory` card showing the LLM-generated text.
- A `Download PDF Advisory` button. The button request posts the same farmer payload to `/api/crop/advisory/pdf`, receives PDF bytes, and offers `krishi_advisory.pdf` for download. This endpoint reruns the full pipeline rather than reusing the already displayed response.
- A `Top 3 Recommended Crops` heading and table. Each row shows rank, crop, confidence, expected yield from the hard-coded lookup, and estimated profit from the hard-coded lookup.
- A `Yield Comparison` Plotly bar chart based on the hard-coded yield dictionary, not a backend agronomy/yield service.
- A `Fertilizer Recommendation` section showing fertilizer type and dosage from the backend response.
- A `Weather` section showing selected location, mapped location, temperature, humidity, and condition in three metric widgets. The mapped weather is fetched again from `/api/weather/<mapped_location>`.
- A footer reading `KRISHI AI | Powered by ML & Weather Data`.

## 4. Backend Features With No Frontend Entry Point

The following capabilities exist in the backend but have no way to be triggered from the current Streamlit UI:

### Orphaned endpoints

1. `POST /api/user/signup` and `POST /api/user/login`: duplicate auth implementation; the UI uses `/api/auth/*` instead.
2. `POST /api/crop/recommend`: the current UI uses `/api/crop/advisory`; the endpoint exists but has no frontend literal call.
3. `POST /api/farm/add`: no farm form or farm request exists in `frontend/app.py`.
4. `GET /api/fertilizer/<crop>`: the UI consumes fertilizer nested in the crop response and never calls this standalone endpoint.
5. `GET /api/soil/data`: no automatic soil-data request is made by the UI; NPK and pH are manually entered.
6. `GET /api/soil/cities`: no city-list request is made by the UI; locations are hard-coded in Streamlit.
7. `GET /api/soil/soil-types`: no soil-type discovery request is made by the UI; soil types are hard-coded in a selectbox.

The following endpoints do have frontend entry points: `/api/auth/signup`, `/api/auth/login`, `/api/history/`, `/api/weather/<city>`, `/api/crop/advisory`, and `/api/crop/advisory/pdf`.

### Orphaned backend modules/capabilities

1. `controllers/voice_controller.py`: backend voice command extraction and raw ML prediction are not exposed by a route and are not imported by the frontend. The frontend performs voice recognition itself.
2. `models/farm_model.get_farms_by_user`: no route or frontend call uses it.
3. `utils/translations.py`: the frontend has its own translation dictionary; no backend caller uses this module.
4. `services.soil_service.fetch_soil_data` as imported in `crop_controller.py`: the controller imports it but directly calls `models.soil_model.get_soil_data` instead. The function is reachable through the soil controller, but not through that crop-controller import.
5. The standalone `test_rag.py` `retrieve()` interface and persisted index are not used by Flask. Flask uses the separate inline-document `services/rag_service.retrieve_knowledge()` implementation.

## 6. Known Issues / TODOs

### Search results

- No literal `TODO` or `FIXME` markers were found in project source outside the virtual environment.
- No genuine commented-out executable code blocks were found. Existing comments are explanatory labels or fallback notes.
- The `print()` calls in the smoke test are intentional test output, not debug leftovers. Backend startup/status prints are functional but should normally use the configured logger.

### Security and configuration issues

1. **JWT secret mismatch and hard-coded secret:** `backend/auth/jwt_handler.py:4` sets `SECRET_KEY = "your_secret_key"` instead of loading the `.env` secret. Its `generate_token` and `verify_token` functions at lines 11 and 16 use this hard-coded value. The active `/api/auth` path therefore does not use the `.env` `SECRET_KEY` consistently.
2. **Second JWT implementation:** `backend/controllers/user_controller.py:7` loads a different `SECRET_KEY` fallback and line 27 creates a token with a different payload shape. This belongs to the orphaned `/api/user/*` route family and increases authentication confusion.
3. **Hard-coded weather API credential:** `backend/services/weather_service.py:10` includes a literal `appid` value in the URL even though line 7 reads `WEATHER_API_KEY`. The environment variable is ignored.
4. **Weak JWT secret warning:** the current `.env` secret is shorter than the recommended 32-byte HMAC key, as shown by runtime `InsecureKeyLengthWarning` messages.
5. **Debug server enabled:** `backend/main.py:113` runs `app.run(debug=True, port=5001)`. This enables the interactive debugger and should not be used for deployment.
6. **Permissive CORS:** `backend/main.py:30` permits all origins for `/api/*`, including authorization headers.

### Error handling and diagnostics

1. **Generic ML strings:** `backend/services/crop_service.py:31` returns `"Model not loaded"`, and line 87 returns `"Prediction error"` rather than a structured error type. The controller passes these strings into a generic JSON message.
2. **Bare middleware exception:** `backend/auth/auth_middleware.py:15` catches every exception while parsing the Authorization header and returns `Invalid token format`, hiding the actual parsing problem.
3. **Bare JWT exception:** `backend/auth/jwt_handler.py:18` catches every exception and returns `None`, hiding expired-token, signature, format, and configuration failures.
4. **Console error printing:** `backend/services/fertilizer_service.py:27` and `:50` print caught errors instead of using the configured logger.
5. **Broad frontend suppression:** `frontend/app.py:346` and `:355` suppress all text-to-speech and microphone exceptions; `:493` suppresses history failures; `:610` suppresses initial weather failures; and `:819` suppresses mapped-weather failures. Users receive fallback behavior but no diagnostic detail.
6. **Global exception masking:** `backend/main.py:91-108` logs the exception but always returns only `Internal server error`, making API debugging dependent on server logs.
7. **No request timeout in backend weather call:** `backend/services/weather_service.py:12` calls `requests.get` without a timeout. The frontend uses timeouts for authentication/recommendation but not all weather/history calls.

### Behavior and data-quality issues

1. **Rainfall input is not used by the existing crop controller:** `backend/controllers/crop_controller.py` derives ML rainfall as `weather.get("humidity", 50) * 3`, ignoring the request's rainfall field. The risk node can inspect the raw rainfall, but the Random Forest does not receive it from the request.
2. **Regional data mismatch:** the location service maps Punjab to the `North` region and the crop controller queries MongoDB using the literal city `Punjab`. MongoDB soil records contain cities such as Amritsar and Ludhiana, so `suitable_crops` is often empty for Punjab-level input.
3. **Case-sensitive suitability reranking:** the crop controller compares `crop_name` to `suitable_crops` without normalizing both sides, while MongoDB initialization stores many crop names with capital letters.
4. **Frontend hard-coded soil values:** the UI defines `/api/soil/*` endpoints but never uses them. NPK and pH are manual defaults, contrary to some project documentation claims of automatic loading.
5. **Duplicate pipeline execution for PDF:** the frontend first calls `/api/crop/advisory`, then the PDF button immediately calls `/api/crop/advisory/pdf`, which runs ML, RAG, and Groq again instead of reusing the displayed result.
6. **RAG duplication:** `services/rag_service.py` stores documents inline and builds an in-memory index; `test_rag.py` separately loads text files and a persisted FAISS index. Updating one knowledge base does not update the other.
7. **PDF storage growth:** `export_advisory_pdf` creates a new file under `backend/generated_reports` for every request and has no cleanup or retention policy.
8. **Model compatibility warning:** the serialized Random Forest was created with a different scikit-learn version than the current environment, producing `InconsistentVersionWarning` at startup.
9. **Frontend chart data is hard-coded:** yield and profit values are local lookup tables, not returned by the ML or agronomy backend.
10. **Frontend and backend location databases are duplicated and can diverge:** `frontend/app.py` and `services/location_service.py` maintain separate lists, aliases, and coordinate behavior.

### Documentation drift

- `README.md` still lists the AI crop recommendation system under future enhancements even though recommendation is implemented.
- `QUICK_START.md` names an old branch and describes automatic NPK loading that the frontend does not perform.
- `STATUS_REPORT.txt` claims ten endpoints, automatic soil loading, Mumbai voice success, and all systems operational, but the current route count, frontend call sites, and hard-coded location list do not support all of those claims.

## 7. Current State Summary

Today, a user can open the Streamlit application, sign up or log in through `/api/auth`, choose a location using the local map or microphone flow, manually enter soil type, NPK, and pH, and click Get Recommendation. The frontend requests current weather, sends the input and JWT to `/api/crop/advisory`, and the Flask backend validates the request, maps coordinates to a known region, fetches weather, runs the Random Forest, filters and reranks the prediction using regional and MongoDB information, stores history, retrieves agronomy documents through a local Sentence Transformer/FAISS service, checks risk conditions, and sends a grounded prompt to Groq for an advisory. Streamlit then speaks the result, shows crop/confidence/risk cards, a risk gauge, advisory text, top-three table, hard-coded yield chart, fertilizer details, and weather metrics, with a PDF download that reruns the pipeline. Several backend capabilities remain unused by the UI, including farm management, standalone fertilizer, soil discovery/auto-loading, duplicate user auth, and the old recommendation route; the app also still has configuration/security mismatches and duplicated data sources that should be resolved before treating it as production-ready.
